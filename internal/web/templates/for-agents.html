How to start
1.Call get_author_profile — learn who you are talking to
2.Call list_skills — see available context categories
3.Ask the user for their session code — a short Polish poetry fragment visible in their dashboard
4.Call bootstrap_session(code, format=full) — receive complete team and skills
5.Call recall(code) — retrieve observations from past sessions
Memory across sessions

At the end of each session, call remember(body, code) to save observations. At the start of the next, call recall(code) to pick up where you left off.

Asking kapoost a question

Use ask_human(question) for things only a human can answer (licensing, intent behind a metaphor, permission to quote). You get an ID back — kapoost answers on his own schedule, anywhere from minutes to days.

Do not block waiting. Persist the ID in your durable memory (or call remember(body=id, code) if you have a session), then poll fetch_answer(id) at the start of future sessions or every few hours. Tight polling is wasted work — answers won't appear faster.

Consulting the team — narada

When your user needs perspectives from multiple experts, you pick the panel and the server supplies the prompts. Choose slugs from list_personas whose expertise the question actually needs, and include at least one persona likely to disagree — a panel assembled only to confirm the premise is worth less than no panel.

Omitting the panel falls back to a keyword manifest. It ranks routes by how many keywords match and anchors matches to word starts, so a term buried inside an unrelated word no longer counts as evidence. What it still cannot do is read an exclusion: a context saying “this is not a security question” matches the security route and seats those personas anyway. Rewording the context to get a different team only reshuffles keyword hits — pass the slugs instead.

Two ways to run it. run_narada(context, personas) — the server speaks. Sonnet 4.6 writes each voice from the persona's own system prompt plus a Haiku 4.5 recap of their journal when they have prior reflections; ~10-15s for a 5-persona parallel fan-out. You get a job id back — poll fetch_narada_result(id) until status is done. Recorded, so it carries a commit tag and feeds the journals.

prepare_narada(context, personas) — you speak, from prompts the server hands you. It returns each persona's ready-to-run SYSTEM and USER block, journal included, and you fan them out to one sub-agent per persona. Session-gated, no model cost, no rate limit. Nothing is recorded: no narada id, no commit tag, no journal learning, so do not invent an id for it. Prefer it when your sub-agents can read material the server never sees — a repository, a failing test, local files — since server-side personas only ever get the context string.

What is never acceptable is the third route: role-playing the personas from memory and presenting that as a narada. Their real prompts and journals are server-side; an improvised panel is your own opinion in five costumes. Both tools exist so you never have to.

Commit tag. When your user later implements one of the recommendations and commits the code, ask them to include [narada:<id>] somewhere in the commit-message. That tag is how /dobranoc traces rollbacks back to the persona that recommended the change, so the persona can write a lesson-for-itself into its journal.

Personas that remember their mistakes

Each persona has an append-only journal at /data/persona-journals/<slug>.md — one file per persona, entries written after their advice was rolled back. Read one with get_persona_journal(slug) (owner token required). Append one with record_persona_reflection(narada_id, persona_slug, error_context); the server does the LLM call in the persona's voice and writes the entry. This is what /dobranoc drives at end of day.
